Codex CLI 搭配免费 LLM API

Codex CLI 需要的配置由清单直接生成，另附真正能配合它工作的免费额度。

Codex CLI 需要什么

Codex CLI 通过 ~/.codex/config.toml 里的一段自定义 model provider 配置，可以调用任何兼容 OpenAI 的端点。

  1. model_provider 指向 [model_providers.*] 下的某一项，两处写法必须完全一致。
  2. env_key 指定持有 key 的环境变量名，因此 key 本身从不进入配置文件。
  3. wire_api 决定请求形态。生成的配置用的是 "responses"；如果服务商文档里只写了 /chat/completions，就改成 "chat"——写错会在第一次请求就以 404 或 schema 错误失败。
  4. 文件必须是用户级的那一份。Codex 会忽略项目级 .codex/config.toml 中重定向服务商认证的键，model_provider 也在其中。

这条命令会生成什么文件

运行 npx free-llm-api setup codex 会写出 config.toml。它由清单生成，所以 base URL 和 model id 都是服务商文档里的原值，不用你再去翻。下面是按 GroqCloud 填好的样子：

# Merge this snippet into ~/.codex/config.toml.
# Project-level config cannot select a custom model provider.
model = "llama-3.3-70b-versatile"
model_provider = "groq"

[model_providers.groq]
name = "GroqCloud OpenAI-compatible gateway"
base_url = "https://api.groq.com/openai/v1"
env_key = "GROQ_API_KEY"
wire_api = "responses"

那个文件里没有 key。值在运行时从 GROQ_API_KEY 读取——就这一个习惯，从结构上保证凭据进不了仓库。

用免费额度该有什么预期

Codex 处理仓库时会发很长的上下文，所以一家「每天请求数」看着很宽松的服务商，仍可能先卡在每天的 token 上限。定下一家之前，两列都要看。

在怪客户端之前，先验 key 本身：浏览器检测页能把「凭据被拒」「被限流」和「端点根本没起来」这三种情况分开，而它们的解法各不相同。
